# Devy feature opportunities

Research snapshot: 11 September 2026. These are proposals, not implemented features. Sources are project READMEs and GitHub repository metadata fetched on this date. Stars indicate reach, not suitability; some popular projects have slowed or stopped development.

## Best next three

1. **A recoverable task workspace.** Give each job a purpose, working branch, CLI conversation ID, provider assignment, and last checkpoint. Offer a reviewed resume action after a rate limit or reboot. This directly addresses the interrupted redesign that prompted this work.
2. **An actionable attention inbox.** Gather permission requests, provider failures, finished changes, and blocked tasks into one persistent list with the context needed to act. Existing waiting-session cards become one view of that list rather than the only representation of pending work.
3. **Provider readiness and routing explanations.** Extend the existing gateway page with persistent probe history and a per-session explanation of the next eligible route. Separate the local account slot's name from the identity/plan reported by the provider; show “unknown” when those details cannot be verified. Distinguish a healthy connector from a usable upstream and distinguish Cloudflare login success from origin reachability.

Implement these as extensions of the current Node/Express, SQLite, tmux, and vanilla-JavaScript architecture. A framework rewrite is not required.

## First release behavior

The first three priorities form one useful phone workflow: understand an interruption, inspect the available recovery, and continue the same task. Start with these bounded slices before adding a full queue or automation system.

| Feature | Concrete screen behavior | Acceptance outcome |
| --- | --- | --- |
| Recoverable task workspace | A task card shows its purpose, repo/branch, last checkpoint time, and whether its agent is still running. “Resume” opens the recovered conversation and route details before launch. Use a task ID independent of the tmux session name. | After a Devy restart, the task still exists. A live agent reconnects without a duplicate launch. A missing agent resumes only when its saved CLI conversation is available; otherwise the UI offers a clearly labeled new session with the saved context. |
| Attention inbox | Each item says what happened, which task it affects, and the available action. Permission items open the current prompt; provider errors open route details; completed work opens its result. Acknowledge and snooze have separate controls. | Acknowledging on the phone persists after reload and is reflected on another device. It does not grant a command permission or mark a task complete. A changed prompt creates fresh attention; a resolved condition closes its stale item. |
| Routing explanations | A session's route sheet shows an ordered explanation such as “A: cooling down; B: needs a different login; C: eligible.” Show the probe's timestamp and result beside each route. Keep “Explain” separate from “Test route,” which makes a real request. | The explanation uses the gateway's actual candidate-selection rules and current session account/protocol. It handles pinned mode and no eligible routes, makes no model request, and labels its answer as current eligibility rather than a guarantee of the next request's success. |

Ship the task record/checkpoint slice first, then the inbox and explanations. Add Web Push after the inbox can deduplicate and resolve events, and add the task queue after task ownership and recovery are reliable. Reusable launch recipes are an independent small win.

## Existing features to build on

Devy already has session discovery and controls, inline replies, a terminal bridge, gateway route ordering/manual switching/fallback, provider probes, route cooldown/error details, token counters and rate-limit summaries, events, projects, AI conversations/memory, Slack triage with acknowledgments/approvals/worktrees, service workers, installable app manifests, and Cloudflare Access validation. The proposals above extend those features; “add a gateway,” “make it a PWA,” and “show active agents” would duplicate current work.

The implementation boundaries were checked against `web/app.js`, `web/gateway.js`, `web-manager/app.js`, `web/sw.js`, `src/gateway-client.ts`, `src/gateway-config.ts`, `src/db.ts`, and `src/slack-agent.ts`. In particular, existing local login-file inspection is not proof that an upstream will accept the next request, and the current page-triggered notifications do not include a service-worker push handler or push subscription registration.
